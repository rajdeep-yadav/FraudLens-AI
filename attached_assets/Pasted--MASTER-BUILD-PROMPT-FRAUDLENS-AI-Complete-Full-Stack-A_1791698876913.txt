# PART 5 — REAL AI FRAUD DETECTION ENGINE

This is the core of the project.

Implement a real fraud detection pipeline that accepts transaction data and returns a prediction or risk assessment.

Do not pretend that a machine-learning model exists when the application only uses manually written rules.

## 5.1 Preferred machine-learning implementation

Use a suitable labeled fraud dataset, preferably a publicly available anonymized financial transaction dataset.

If downloading data is not possible, create a synthetic dataset with explicitly documented generation assumptions.

Train a classification model using scikit-learn. Start with logistic regression or random forest and compare against an appropriate baseline when feasible.

The pipeline must include:
1. Data loading.
2. Schema and data validation.
3. Feature preparation.
4. Training and test separation.
5. Class imbalance handling.
6. Model training.
7. Model persistence.
8. Prediction.
9. Evaluation.
10. Version identification.

Avoid data leakage. Split data before fitting preprocessing transformations and before any resampling operation.

Where possible, use stratified splitting or time-based splitting appropriate to the dataset.

Evaluate using:
- Precision.
- Recall.
- F1-score.
- ROC-AUC.
- Precision-recall AUC for highly imbalanced data.
- Confusion matrix.

Explain why accuracy alone is insufficient when fraud is rare.

Do not fabricate evaluation results. Calculate all displayed metrics from actual test predictions.

Only display a probability as a probability when the model produces an appropriate probability estimate. If calibration has not been assessed, document that limitation.

## 5.2 Prediction features

Use only features supported by the dataset or supplied transaction context.

Potential features include:
- Transaction amount.
- Time of transaction.
- Merchant category.
- Payment method.
- Transaction frequency over a defined window.
- Deviation from known customer behavior.
- Device novelty.
- Geographic inconsistency.
- Failed-attempt count.

Do not invent customer history, device reputation, transaction frequency, or geographic distance when the necessary data is unavailable.

Create a feature preparation pipeline that ensures the same transformations are used during training and inference.

## 5.3 Explainable predictions

Every prediction should return:
- Risk score.
- Risk category.
- Model version.
- Contributing features or triggered rules.
- Recommended action.
- A clear explanation of the result.

Use genuine feature attribution where feasible. For a simpler model, explain actual model coefficients or feature importance with appropriate caveats.

For rule-based fallback predictions, return the exact rules that triggered.

Do not fabricate SHAP explanations or claim that a feature caused fraud when the model only identified an association.

## 5.4 Rule-based fallback

The application must remain usable if the machine-learning runtime cannot start.

Implement a separate, modular rule-based scoring engine.

Possible rules:
- Unusually large transaction amount.
- Rapid transactions within a defined time window.
- Repeated failed attempts.
- Unusual location compared with known history.
- New device.
- Unusual merchant category.

Only execute rules for which the necessary information exists.

Use configurable weights and thresholds. Document the formula and the limitations.

Label the output clearly as rule-based risk scoring.

## 5.5 Risk classification

Create configurable risk categories such as:
- Low.
- Medium.
- High.
- Critical.

Store thresholds in the backend configuration or database.

Ensure threshold changes affect future predictions.

Distinguish these concepts:
- Risk score.
- Predicted fraud probability.
- Human-confirmed fraud.
- Investigation outcome.

They must never be treated as equivalent.

## 5.6 Human oversight

A high-risk prediction should create a review recommendation, not automatically declare the customer guilty or permanently block a transaction.

Provide an analyst workflow to record whether a transaction is:
- Pending review.
- Confirmed fraud.
- Legitimate.
- Inconclusive.

Preserve the original model prediction even after the analyst changes the final outcome.
